# ADR-028：V2 结构简化 —— 移除应用快照、指令目录与授权记录

- 状态：已接受
- 日期：2026-09-03
- 取代：[ADR-026](ADR-026-application-catalog-snapshots.md)、[ADR-027](ADR-027-unified-real-run-authorization.md)

## 背景

V1 在只有一个应用时按 N 个应用设计，并且照搬了商业 RPA 产品（影刀一类）的元素库 / 指令库 / 授权审核结构。

实测到的规模：

| 部分 | 行数 |
| --- | --- |
| `rpa-core` Python | 9,003 |
| `rpa-core` JSON Schema | 1,702 |
| `rpa-core` 测试 | 5,496 |
| 应用源码 | 2,912 |
| 应用测试 | 1,909 |
| 治理文档 | 4,936 |
| **合计** | **≈25,958** |
| **真正操作浏览器的业务逻辑** | **561** |

而 agent 生成应用时，时间主要花在申请授权和产出报告，不是花在解决自动化难题。

## 决策

### 1. 移除授权记录子系统

`authorization.py`(1504) + 测试(792) + `authorization-record.schema.json`(560) = 2856 行。

浏览器边界的全部检查是四条：动作在允许列表、step 在允许列表、element 在允许列表、origin 在允许列表。而正常运行时 scope 被构造为 `element_ids = 全部元素`、`browser_actions = tuple(BrowserAction)`、`step_ids = 全部步骤` —— `BrowserActions` 的 API 本来就只接受目录里的 `ElementSpec`、只有那几个方法、只在登录站点上，四条检查恒为真。

更关键的是它防不住它要防的东西：危险藏在 `[locator]` 那行选择器里，而那行是 agent 自己写的。守卫校验的是"你做的和你说的一致吗"，而手滑的定义恰恰是"说的就是错的"。

取代方案见 ADR-028 的"安全边界"部分：只读子账号（平台侧）+ `--live` 二分 + 交互确认 + 写后回读。

### 2. 移除应用快照与指令目录

跨应用资产复用从未发生。第二个应用确定换平台，届时 7 条指令和 17 个元素的可复用数量为 **0** —— `catalog.py`(775) + 锁文件 + 依赖闭包 + 回灌工作流会搬运不了任何东西。

Instruction 层同时被移除：它用 TOML 声明 + 字符串 ID 查表 + 手写依赖闭包 + 手写版本，重新实现了一个比 Python 自带的更差的模块系统（丢掉 IDE 跳转、类型检查、重构和 `git grep`）。

### 3. 元素库保留并加强

元素库的核心价值不是跨应用共享 XPath，是**页面改版时在一个地方修好，所有引用点跟着好**。这个需求在 agent 场景下只强不弱。

保留形态：应用内单个 `elements.toml` + `expect_count` + `rpa-app verify-elements`。

`expect_count` 与 V1 `[verification]` 块的本质区别：前者是**现在应该成立的断言**，能发现失效；后者是**过去某一时刻的记录**，今天什么也不保证。

## 结果

- 直接删除约 10,000 行；剩余的 `catalog.py` / `instructions.py` / `requirements.py` / `discovery.py` 等待第二个应用证明未被使用后再删
- 代价：跨应用复用需要人工 `git grep` 加复制。在只有一到两个应用、且平台各不相同时，这个代价低于维护一套包管理器
- 风险：日后应用增多、平台重复时，可能需要重新引入某种共享机制。届时的判据是"第三个应用真的重复了同一段代码"，而不是预先设计

## 被否决方案

- **保留授权记录但收窄 scope**：收窄后仍然校验 agent 自己写的声明，对真实风险无效，只是让恒真检查变成偶尔为假的检查
- **保留 catalog 但去掉锁文件**：依赖闭包和版本仍在，复杂度的大头没有消失
- **等第二个应用写完再决定**：授权和 catalog 的无效性已经由代码和实测证据确定，不需要再等一轮
