# 运行隔离与安全边界

## 安全边界按实际有效性排序

V1 用 2856 行构造了一套授权记录系统，其浏览器边界的四条检查在正常运行时恒为真，而且**防不住它要防的东西** —— 危险藏在定位器里，那行是 agent 自己写的；守卫校验的是"你做的和你说的一致吗"，而手滑的定义恰恰是"说的就是错的"。

V2 的边界按有效性排序：

### 1. 只读子账号（唯一真正的边界）

**每接入一个新平台，第一件事是申请只有查询和导出权限的子账号。**

这是唯一在代码之外的边界 —— 它连你的代码写错了都拦得住，且零维护成本。任何代码内的守卫都做不到这一点。

拿不到只读账号的平台，在 `app.toml` 显式标记，并在 `requirement.md` 写明风险由谁承担。

### 2. 默认 / `--live` 二分 + 交互确认

- **默认**：浏览器读取、筛选、下载可以执行；外部业务写入（飞书 / 数据库 / 正式 Excel / NAS / 告警）转为 `runs/<run_id>/write-previews/` 下的本地预览，并校验字段、类型、唯一键、范围、数量和目标位置
- **`--live`**：允许已声明的外部写入。启动前展示账号、目标、写入步骤和预计记录数，要求一次 `y/N`。非交互环境不自动确认
- 适配器在真正产生副作用前再次校验模式。CLI 检查通过不代替适配器门禁

### 3. 写后回读

Live 写入完成后必须独立查回来，比对记录数和内容摘要。写接口返回成功不等于写入成功。

## 运行目录隔离

每次 `run` 或 `resume` 使用应用本地、Git 忽略的 `runs/<run_id>/`：

- `run_id` 是 1 至 128 字符的安全单目录组件
- 运行目录精确等于当前应用的 `runs/<run_id>`，不能由调用方声明任意外部根目录
- checkpoint、event logger 和声明运行路径的服务与同一 `ExecutionContext` 精确绑定
- checkpoint / event 拒绝最终路径的符号链接和硬链接；预览拒绝 `runs`、运行目录及预览目录符号链接
- 同一 `run_id` 从读取 checkpoint 到 cleanup 全程持有跨进程排他锁
- 不同步骤使用独立预览文件名；同一步重试才允许原子替换自己的预览

排他锁使用 POSIX `flock`，不支持时 fail-closed。Windows 运行机必须先实现并验证等价的进程退出自动释放锁。

## 多账号浏览器隔离

每个账号或店铺必须对应：

```text
一个独立 Chrome 进程
+ 一个持久化 Profile
+ 一个动态租用的调试端口
+ 一把 Profile 排他锁
+ 一个独立运行目录
+ 一套独立检查点
```

不得让不同账号共享 Profile、Cookie、端口租约或检查点。

`BrowserManager` 负责解析浏览器路径、租用端口、获取 Profile 排他锁、启动或连接浏览器、按生命周期策略保留或结束进程、释放端口与锁。业务应用不能决定浏览器进程何时退出。

生命周期策略：

- `KEEP_OPEN` —— 本地开发和人工验证默认使用，方便处理验证码并检查页面
- `REUSE_UNTIL_IDLE` —— 统一运行机器复用浏览器，空闲后回收
- `TERMINATE_ON_FINISH` —— 只有明确配置时使用

生命周期策略不改变 Profile 排他要求。

## 人机验证

遇到验证码、滑块、短信或其他风控：

1. 停止当前自动动作
2. 记录 `HumanVerificationRequired`
3. 保存脱敏截图和页面上下文
4. 保持浏览器供人工处理，除非生命周期策略另有明确要求
5. **不模拟绕过、不调用第三方打码服务**
6. 人工处理后按恢复策略重新验证状态

## 凭据与脱敏

- 账号密码集中保存在应用本地 `.env`
- 账号别名、平台、环境变量名和 Profile 映射保存在 `config/stores.local.toml`
- `.env`、`config/stores.local.toml`、`profiles/`、`runs/` 不提交
- 可提交文件用稳定别名（`STORE_001`）和占位符
- `SecretValue` 的 `str()` 和 `repr()` 都不泄露运行时值；日志只记录字段名或掩码
