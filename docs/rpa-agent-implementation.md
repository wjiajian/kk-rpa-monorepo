## 1. 目标与范围

用户提供业务需求与运行参数，Agent 基于框架生成独立 Python 应用。固定流程由程序执行；失败时 Agent 能读懂步骤要求、连接运行上下文、处理当前页面，并将实际输出交回框架校验。

本轮改进针对已出现的开发成本：步骤输出格式仍需翻阅 execute/verify，接管脚本还要手动加载配置、重建 ExecutionContext 并连接 BrowserManager。

保留现有五个 CLI 命令及 run/resume 语义。后续调度器、自动故障分类、全局元素平台、指令注册表、自定义流程语言、写入补偿和共享下载目录并发协调均不在本轮范围。飞书、数据库等真实适配仍随具体应用需求落地。

## 3. 已落实的文档约定

- 正式流程的页面目标保存在应用 elements.toml；不要求登记整站元素。
- 一次接管使用的引导提示、临时弹窗等辅助目标，可根据实际 DOM 构造临时 ElementSpec，通过 ctx.browser 操作并留证。
- 临时辅助目标不会自动写入元素库；--locator-overrides 仍只用于覆盖已有元素 ID 的定位字段。
- 条件、循环、变量和数据处理使用 Python。基础操作封装实际的等待、回读、下载或错误处理；应用专有业务函数保留在应用内。
- Step 的成功条件决定是否继续。临时操作和定位器变化不改变账号、日期、品牌、报表等业务要求。

这些约定同步到 AGENTS.md、领域术语、LLM Wiki 和应用生成技能，供后续 Agent 开发使用。

## 4. T1：补齐每步契约

状态：已完成。聚水潭 S000–S005、京麦 S001–S006 已逐步列出目标、输入来源、前置状态、输出类型、接管示例、实际 verify 条件和失败恢复要求。动作记录与实际回读条件分别说明，沿用现有业务验证。

### 交付内容

在两个应用各自的 requirement.md 中补齐每步说明，不新增独立步骤注册文件或另一份需求规范。

| 内容 | 应明确的信息 |
| --- | --- |
| 业务目标 | 该步完成什么业务进展 |
| 输入 | 从 ctx.inputs、前序成功输出或运行服务中读取哪些值 |
| 前置状态 | 需要的账号、页面、选中条件、文件或已生成报表 |
| 输出 | execute 返回字段的名称、类型、含义；可提交 Agent 结果的示例 |
| 成功条件 | verify 实际回读哪些信息、与哪些原输入比较 |
| 失败与恢复 | 动作失败、结果不符、页面丢失分别应检查什么 |

例如，聚水潭 S003 当前契约可以写为：

- 输入：原任务的 ctx.inputs.brand_value；前序账号检查和商品库存导航已成功。
- 动作：重置历史筛选，将品牌选择归一为目标品牌。
- 输出：requested_brand 为字符串；selected_brands 为回读的字符串列表。
- 校验：requested_brand 与原任务目标一致；输出及当前页面的选中品牌经归一后，集合均只包含目标品牌。
- 接管：Agent 先完成相同业务要求，再提交实际输出；页面引导可以临时关闭。若 verify 的定位器失效，可为本次续跑覆盖定位字段。

示例中的 BRAND_TARGET 是占位符，执行时必须使用原运行参数中的实际值：

```json
{
  "requested_brand": "BRAND_TARGET",
  "selected_brands": ["BRAND_TARGET"]
}
```

说明与 execute/verify 不一致时，依据业务需求修正具体差异，不能把预期动作写成已经被校验的结果。首轮通过现有代码、需求说明和测试保持一致，不引入通用 schema 引擎或 Step 元数据注册系统。

### 验收标准

1. 聚水潭 S000–S005、京麦 S001–S006 均有上述说明，字段名称与当前代码一致。
2. 读者可以从步骤说明确定接管结果格式、必需页面状态和应保持的原任务条件。
3. 每步保留正常场景与至少一个 execute 成功、verify 拒绝的结果反例；新增测试只覆盖发现的实际缺口。

主要文件：两个应用的 requirement.md、program.py/steps.py 与 test_program.py，以及 [应用生成规则](../.agents/skills/rpa-app-generator/references/application-generation.md)。业务代码只在发现契约不符时修改。

## 5. T2：提供统一接管上下文入口

状态：已实现，通过离线及 macOS 真实验证。核心回归覆盖源参数保留、服务注入、不执行步骤、不改源结果、拒绝不完整记录、异常诊断及释放占用后的接管和续跑。真实接管验证了未接回原浏览器时如实报告、正常退出后重新接回，以及处理异常后仍能 resume。

### 公开接口

现有 rpa_core.cli 提供 `open_recovery_session(application, run_id, *, credentials=None)`。输入使用当前 ApplicationDefinition、源失败 run_id 和可选本次凭据，不增加新的 CLI 命令：

```python
from rpa_core.cli import open_recovery_session

with open_recovery_session(APPLICATION, run_id, credentials=credentials) as recovery:
    ctx = recovery.context
    # 查看原输入、成功输出和当前页面；临时处理仍使用 ctx.browser。
    # 根据实际回读构造该步输出，保存到忽略的本地 JSON 文件。

# 退出接管会话后，再调用现有 resume 提交输出或指定重新执行的位置。
```

返回 RecoverySession 的 context、source_record 和 browser_adopted 三个字段。context 的 inputs 和 outputs 与读取的源记录分别复制，临时修改不会改写源 result.json。接管事件追加到源目录的 recovery-events.jsonl，不生成成功结果；browser_adopted 不证明账号或页面可用。

### 行为要求

| 阶段 | 要求 |
| --- | --- |
| 读取记录 | 复用源记录目录和应用身份检查；成功记录或其他应用的记录不能当作本应用失败任务接管 |
| 构建上下文 | 保持原账号、运行模式、业务 inputs、下载目录及已完成输出；凭据由本次传入或本地配置加载 |
| 不完整记录 | 缺少已保存 inputs 等必要信息时，返回明确原因，指导补齐参数后新 run；不推断丢失参数 |
| 连接浏览器 | 复用 BrowserManager 的 Profile、端口和接管记录；报告是否接回原浏览器。未接回时由 Agent 检查并恢复页面，入口不自动执行历史步骤 |
| 页面处理 | 提供 ctx.browser 和应用服务；允许操作经过实际确认的临时辅助目标。仅打开接管会话不会登录、导出或执行任何 Step |
| 状态与证据 | 沿用 runs 中的证据组织方式，不修改源 result.json 或把步骤标记为成功；错误沿用现有诊断结构 |
| 退出会话 | 正常退出或处理异常均释放接管持有的锁和连接资源，保留可供 resume 连接的浏览器；沿用现有生命周期机制 |
| 提交结果 | 会话退出并释放 Profile 占用后，使用现有 resume；成功判定统一交给 Runner 和原 verify |

接管脚本结束不等于任务成功。普通 run/resume 成功后仍关闭浏览器。验收工具若会在单次命令结束时回收浏览器子进程，使用持续终端完成连接、临时处理和续跑；本轮不为此建设后台驻留服务。

### 实施位置

- [cli.py](../packages/rpa-core/src/rpa_core/cli.py)：拆分可共用的失败记录读取与上下文准备代码。恢复点选择及 validate_resume 仍由 resume 执行；公开辅助入口不调用 execute。
- [browser_manager.py](../packages/rpa-core/src/rpa_core/browser_manager.py)：复用 start、detach 和现有接管记录；只补充新入口需要的行为，不增加第二套浏览器管理器。
- [runtime.py](../packages/rpa-core/src/rpa_core/runtime.py)：保留 Runner 对原输出、verify、恢复前缀和 locator_overrides 的处理，避免另写接管成功判定。
- 两个应用继续导出现有 APPLICATION，接管使用相同 load_runtime_options/build_services，不另设应用恢复配置。

### 验收标准

1. 两个应用的接管示例均通过公开入口获得 ctx，不再自行装配 ExecutionContext、BrowserLaunchSpec、Profile 锁和端口。
2. 修改本地品牌、日期默认值或下载配置后，接管与 resume 仍使用源任务的业务参数和目录；凭据不进入运行结果或诊断输出。
3. 打开和关闭接管会话不会执行步骤、创建报表或改变源 result.json；处理代码抛错后仍可再次接管或 resume。
4. 退出后无遗留锁占用，保留的浏览器可以被 resume 接回；丢失页面或会话时不会直接宣称恢复成功。
5. 错误接管输出、verify 异常、临时定位器改变验收字段、再次续跑误继承覆盖等已有拒绝场景继续有效。

相关测试放在现有核心测试中；如果接管入口形成独立模块，再按模块组织测试。无需为了目录形式提前拆分类型或增加兼容层。
